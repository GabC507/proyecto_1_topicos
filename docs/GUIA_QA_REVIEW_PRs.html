Lista de QA manual

Probar con datos locales/demo; no usar datos reales de clientes. El panel requiere el valor local de ADMIN_TOKEN; no incluirlo en capturas ni reportes.

Datos guardados · PR #3

  • Sin consentimiento, reservar y recargar: no debe recordar nombre/teléfono.
  • Con consentimiento y reserva exitosa, recargar: debe autocompletar. Borrar desde la interfaz y comprobar que desaparece.
  • Confirmar que solo se guarda contacto en ese navegador; no notas ni datos de pago.

Calendario · PR #4

  • Comprobar estados disponible, parcialmente ocupado, completo y sin horarios; navegar meses y probar en móvil.
  • Probar día cerrado, sin disponibilidad, error de red y doble intento concurrente. La API debe rechazar el horario tomado con 409.

Previsión · main

  • Sin historial, el panel debe indicar falta de datos. Con datos demo, verificar promedio por mismo día de semana y exclusión de cancelaciones.
  • Sin token admin debe denegar acceso; con token debe cargar. Revisar móvil/escritorio.

Gestión segura · PR #1

  • Probar código privado incorrecto y correcto. Un teléfono por sí solo no debe revelar ni permitir cambiar citas.
  • Reprogramar a horario libre: éxito. Horario ocupado, pasado o cerrado: rechazo. Cancelar cita futura y confirmar que libera el horario.

Bloqueos y fix +507 · PR #2

  • Sin token admin, listar/crear/eliminar bloqueos debe denegarse.
  • Probar intervalo y día completo: desaparecen del calendario y una reserva directa a la API devuelve 409. Retirar bloqueo y verificar que se libera.
  • Intentar bloquear una cita activa: debe rechazarse sin cambiar la cita.
  • Reservar con +507 6123 4567: debe aceptar y normalizar. Con teléfono inválido, mostrar el campo/motivo, conservar la hora y permitir corregir.

Checklist del Reviewer

  • Confirmar que base/head corresponden al orden de la página 1 y revisar el diff completo del PR.
  • Verificar autorización admin, privacidad, consentimiento, hash del código privado y que no haya secretos/datos personales.
  • Comprobar las reglas en backend además del frontend; una hora bloqueada/ocupada tampoco debe reservarse con petición directa.
  • Revisar límites, errores, ausencia de datos, solapamientos y que las pruebas cubran el cambio.
  • Dejar comentarios reproducibles. Si solicita cambios, revisar la nueva versión antes de aprobar.
Gate de merge: evidencia QA adjunta + Reviewer aprueba + comentarios bloqueantes resueltos + tests pasando. No integrar fuera del orden #3 → #4 → #1 → #2.
